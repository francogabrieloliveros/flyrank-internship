| **The Problem**<br><br>Artists hit a slump: running out of ideas, not wanting to draw, forgetting the fun in drawing — especially for professionals. That's not a skill problem. It's a fun problem.<br><br>Drawing alone and drawing with others are a different kind of fun. I wanted people to get that fun back — to draw with others and learn how they approach art. So the canvas had to be a free canvas. No taking turns, no directions. Just a blank canvas, open to whoever's there.<br><br>**What I Did and Decided**<br><br>Event-driven, not request-response. The canvas drawing needed to be highly event-driven. If users had to click a button to send or receive their drawing, it would ruin the UX. So I built it on Node.js and Socket.IO from the start — my first backend project, and I went straight for websockets and concurrency instead of something simpler. I don't fully know why I made that choice for a first backend project, but it's the reason the collaboration actually feels live.<br><br>One array as the source of truth. Every stroke's coordinates go into an array as it's drawn. That array is the canvas — everything a client sees is just that array being drawn out.<br><br>Solving concurrency was the hardest part. With no turns and no directions, things broke fast: canvases having the same strokes, canvases having different colors and stroke widths, strokes on one user's canvas not matching the coordinates on another's. The fix was making sure every stroke carried full detail — coordinates, color, canvas size, brush size — so it could be perfectly replicated on another canvas. I normalized coordinates against canvas size, which made the canvas a 1:1 replica across different screen sizes. That's fully solved.<br><br>New users joining had the same root fix. Before, users who joined didn't see the previous strokes. Since I already had every coordinate in an array, I made it so that array gets drawn first for anyone who joins — so every user sees the exact same drawing, whenever they join.<br><br>Load testing, to find the limit, not fix it. | **The Problem**<br><br>Not every person understands sign language. That's the whole gap. We wanted a glove that could bridge sign language speakers and non-sign language speakers — but the obvious fix, a camera reading the signer, assumes the other person is holding a camera up every time they need to communicate. They're not. So the translation had to live on the signer's own hand, not depend on someone else's setup.<br><br>**What I Did and Decided**<br><br>Flex sensors alone could only tell us how bent a finger is and which fingers are bent — that's it. Sign language involves tilting the hands and moving the whole arm, so flex sensors by themselves were only reading half the sentence. That's why we added an accelerometer: to capture the motion and rotation flex sensors couldn't see.<br><br>I built the hardware end-to-end and wrote the threshold logic myself, since I had direct access to the sensors. Each finger got encoded into three states — 0 for not bent, 1 for slight bend, 2 for bent — stored in an array where index 0 was the thumb, index 1 the index finger, and so on. I paired that with a handPos value — 0 for palm forward, 1 for downward, 2 for sideward — so shape and orientation worked together as one signature per gesture.<br><br>The matching logic itself changed shape too. At first we stacked if-statements, but it got too slow checking every condition in sequence. So I moved to arrays instead — I was limited to that structure since it was my first programming experience, but it worked: comparing a signature as a whole is faster than testing conditions one at a time.<br><br>We also didn't trust a stopwatch to measure latency, because it introduces human inconsistency on both ends of the click. So we recorded video instead, manually cutting to the frame the gesture was completed and the frame the MP3 module made its first sound, using the FPS to keep the timing accurate.<br><br>**What Came of It**<br><br>The array-based matching brought average latency down to 0.98 seconds, with a peak response of 0.44 seconds. We translated 26 of 37 ASL gestures correctly — 73.7% accuracy — which landed us in the "Accurate" band (70–85%) on our professor's rubric, one tier below "Excellent." The project won Best Research for our batch.<br><br>The 11 gestures that failed weren't random — they were gestures with the same fingers bent but to different degrees, or the exact same finger gestures with different hand rotation. It could've been fixed through more fine-tuning, but this was my first programming and electronics project, and we were building a prototype, so we settled for this. Underneath that, the accelerometer didn't really give us helpful results — our wiring quality suffered from cheap solder, and our calibration was static, so a lot of the time similar finger bends couldn't be differentiated by their orientation.<br><br>Looking at the code now with more experience, the gesture-checking itself is what I'd rebuild — moving off individual checks per gesture toward a hashmap would make the lookup shorter and the code more readable than what we had. | **The Problem**<br><br>Not every person understands sign language. The lat/long also fed into range-based suggestions, so users could get notified about food posts near their area with a radius they set themselves.<br><br>For the recipe engine, every time a user hits "suggest a recipe," the food name and description get injected into a prompt sent to the Gemini API, which suggests a recipe using that specific food. I fetch the user's identity, then use a Firestore `where` query to filter by owner server-side rather than looping through everything client-side — that's Firestore's own abstraction handling the lookup, not something I built myself.
